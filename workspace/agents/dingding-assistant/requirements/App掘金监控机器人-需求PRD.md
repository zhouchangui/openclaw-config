# App 掘金监控机器人（Fast-Follower Bot）

## 基本信息
- **类型**：智能体开发
- **状态**：新建
- **优先级**：P1（高）
- **工作量**：中等
- **分类**：Market Research
- **创建日期**：2026-03-11

---

## 需求概述

开发一个自动化的市场调研智能体，定时监控 App Store 榜单、抓取用户评论，并利用 AI 分析寻找具有盈利潜力的“可复制/优化”的工具类 App，输出直接可用于产品立项和跟进的建议报告。

---

## 需求来源

用户提供了一份极简版 PRD，核心意图是：
- 自动发现海外/国内 App Store 榜单上的新锐工具型 App
- 通过中低星评论提炼用户痛点
- 识别竞品的收费模式和付费意愿
- 自动生成结构化分析结果并定时推送到指定终端

---

## PRD 摘要

### 1. 产品概述
- **产品名称**：App 掘金监控机器人（Fast-Follower Bot）
- **产品定位**：自动化市场调研工具
- **核心价值**：省去人工盯盘时间，自动化挖掘用户痛点，并输出商业产品立项建议

### 2. 核心目标
- **发现新锐**：第一时间发现海外/国内榜单上突然蹿红的新工具
- **找准痛点**：通过分析差评，找出竞品没做好的地方
- **摸清钱脉**：扒出竞品收费模式，验证真实付费意愿

### 3. 核心功能需求

#### 模块一：榜单数据抓取（Data Fetching）
- 支持设定特定国家/地区（如美区、日区）
- 支持设定特定分类（如效率工具、图形与设计、健康健美）
- 获取免费榜或畅销榜近期排名飙升的 Top 20-50 应用名单
- 提取基础信息：
  - App 名称
  - 开发商
  - 应用描述
  - 当前排名
  - 上架时间
- 提取商业模式：
  - App 内购买项目（IAP）
  - 价格信息（如月订阅、终身买断）

#### 模块二：用户评论采编（Reviews Scraping）
- 针对每个上榜 App，抓取最近 100 条有效评论
- 重点筛选 1 星到 3 星评价，作为痛点分析核心样本

#### 模块三：AI 智能分析（AI Analysis）
- 将应用描述与评论数据交给大模型分析
- 输出核心指标：
  - **一句懂产品**：一句话概括工具本质
  - **核心痛点提炼**：用户在抱怨什么
  - **复制建议评估**：基于技术复杂度与用户需求给出跟进评级

#### 模块四：定时任务与消息推送（Automation & Notification）
- 支持 Cron 定时执行（例如每周一、周四上午 9:00）
- 支持结构化推送到：
  - 飞书群机器人 / 私聊
  - 钉钉
  - 微信
  - Notion
  - 飞书多维表格

### 4. 业务工作流

```text
[定时触发器]
      ↓
[读取 App Store RSS/API] → 获取指定地区/分类的飙升名单
      ↓
[循环抓取单个 App] → 获取价格 / IAP / 近100条中低星评论
      ↓
[打包给 AI] → 输出功能本质、用户痛点、跟进建议
      ↓
[生成标准化报告] → Markdown 或结构化表格
      ↓
[推送终端] → 飞书 / 钉钉 / 微信 / Notion / Bitable
```

### 5. 预期交付物

机器人最终推送的消息应至少包含：
- App 名称
- 当前排名与变化
- 收费模式
- 一句话简介
- 主要用户痛点（含提及率）
- 跟进建议（可复制点 / 差异化机会）
- App Store 链接

## Brainstorm 分析

### 需求理解

这不是一个通用信息摘要 Agent，而是一个**面向“找可抄可超的工具型 App”场景的选品/市场情报 Agent**。

#### 主要问题
- [ ] 如何稳定获取指定地区、指定分类、指定榜单的 App 数据源
- [ ] 如何高质量抓取评论与 IAP 信息，并控制采样质量
- [ ] 如何把“用户痛点 + 付费模式 + 技术复杂度”转成可执行的产品跟进建议

### 初步设计方向
- 优先做成“定时巡检 + 结构化报告”的研究型 Agent
- 输出优先面向飞书消息 / Markdown 报告 / 多维表格记录
- 第一阶段先聚焦单平台（App Store），覆盖主要市场地区
- 第二阶段再扩展更多数据源（如 Google Play）、更复杂的评分模型和结构化落表

### 关键执行约束（硬规则）
- **每次执行必须创建独立临时目录**，作为本次任务工作区
- **先写实现计划文件**，明确阶段、检查点、输出文件路径
- **采集数据必须优先落文件**，而不是把大量原始数据堆在上下文里
- **最终由 LLM 基于文件内容编写报告**，避免直接在长上下文里拼接总结
- **要妥善管理上下文**，必要时使用子智能体分段采集/分析，避免上下文爆炸影响结果正确性
- **最终报告必须使用稳定模板输出**，保证结构一致、可复用、可比较

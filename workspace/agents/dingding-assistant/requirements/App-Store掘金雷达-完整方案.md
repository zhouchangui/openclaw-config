# App Store 掘金雷达（Fast-Follower Bot）完整方案

## 1. 方案概述

### 1.1 产品定位
App Store 掘金雷达是一个**面向产品选品与 fast-follower 决策的研究型 Agent**。

它的目标不是做泛资讯摘要，也不是简单播报榜单，而是持续从 App Store 主要市场中筛出**值得跟进的工具类 App 机会点**，并输出一份**稳定、可复用、可比较**的 Markdown 报告。

### 1.2 核心价值
- 自动发现 App Store 主要市场中的潜力工具 App
- 自动分析其商业模式、用户差评痛点与可优化空间
- 为后续产品立项提供结构化输入
- 用文件中间态控制上下文，保证分析稳定性与结果正确性

---

## 2. 首版范围（已确认）

### 2.1 监控平台
- **一期只做 App Store**
- Google Play 作为二期扩展，不进入首版

### 2.2 监控地区
首版覆盖主要市场地区：
- 美国
- 日本
- 中国
- 中国香港
- 中国台湾
- 韩国
- 英国
- 德国
- 法国
- 加拿大
- 澳大利亚
- 新加坡

### 2.3 监控类别
- **工具类优先**
- 首版重点可聚焦：效率、图形设计、商务、开发者工具等工具型场景

### 2.4 运行频率
- **工作日每天 1 次**
- 首版也支持手动触发

### 2.5 输出方式
- **第一层输出**：飞书消息摘要（Top 3）
- **第二层输出**：本地 Markdown 完整报告
- 首版暂不接飞书多维表格 / Notion

---

## 3. 首版核心目标

这个 Agent 每次执行，需要最终回答清楚以下问题：

1. **它在做什么？**
2. **它为什么值得关注？**
3. **它靠什么赚钱？**
4. **用户在抱怨什么？**
5. **我们有没有机会做得更好？**

最终输出不是原始数据堆积，而是：
- 候选 App 排名
- 一句话机会判断
- 核心痛点提炼
- 跟进建议
- 结构化报告

---

## 4. 关键执行约束（硬规则）

这是首版设计里的强约束，后续实现必须遵守：

1. **每次执行必须创建独立临时目录**
   - 作为该次扫描任务的唯一工作区
   - 不同 run 之间不能混用文件

2. **先写实现计划文件**
   - 在开始抓取和分析前，必须先生成 `plan.md`
   - 计划文件中明确本次任务范围、阶段、输出路径、检查点

3. **采集数据必须优先落文件**
   - 榜单数据、App 详情、评论、价格、分析结果都应写入文件
   - 不允许把大批原始数据直接堆在上下文中处理

4. **最终由 LLM 基于文件编写报告**
   - LLM 只在最后统一读取中间文件，产出最终 Markdown 报告
   - 避免长链路上下文拼接导致分析失真

5. **要妥善管理上下文**
   - 对于多地区、多 App 的采集与分析，必要时应适当使用子智能体
   - 子智能体负责分段采集或局部分析，结果统一回写文件
   - 主 Agent 最后只汇总必要信息，防止上下文爆炸

6. **报告格式必须稳定**
   - 最终输出必须使用固定 Markdown 模板
   - 每次输出字段顺序和结构尽量一致，方便横向比对与自动处理

## 5. 总体执行流程

建议采用五段式执行架构：

```text
初始化任务目录
  ↓
写入实现计划 plan.md
  ↓
分段采集并落文件（榜单 / App 详情 / 评论 / IAP）
  ↓
生成中间分析文件（候选池 / 评分结果 / 痛点摘要）
  ↓
LLM 读取文件并按模板输出 Markdown 报告
```

### 5.1 阶段说明

#### 阶段 A：初始化
- 创建唯一 `run_id`
- 创建本次任务临时目录
- 初始化目录结构
- 生成 `plan.md`

#### 阶段 B：榜单与 App 基础信息采集
- 根据配置扫描目标地区与工具类榜单
- 获取候选 App 列表
- 记录 App 名称、开发商、描述、榜单位置、链接、上架时间等

#### 阶段 C：评论与商业模式采集
- 为候选 App 抓取评论样本
- 重点提取 1~3 星中低分评价
- 抓取 IAP / 订阅 / 买断价格信息

#### 阶段 D：候选评分与机会判断
- 生成候选池
- 计算机会分
- 提炼痛点与建议

#### 阶段 E：模板化报告输出
- 输出飞书 Top 3 摘要
- 输出本地 `report.md`

## 6. 运行目录与文件规范

每次执行都创建单独目录，例如：

```text
data/workspace/{run_id}/
├── plan.md
├── inputs/
│   ├── config.json
│   └── target-markets.json
├── raw/
│   ├── rankings.json
│   ├── app-details.json
│   ├── reviews.json
│   └── pricing.json
├── analysis/
│   ├── candidate-pool.json
│   ├── scored-apps.json
│   └── insights.md
└── outputs/
    ├── report.md
    └── summary.json
```

### 6.1 文件职责说明

#### `plan.md`
必须先写，记录：
- 本次执行时间
- 目标地区
- 榜单类型
- 扫描类别
- 任务阶段
- 待办清单
- 输出文件路径
- 当前执行状态

#### `inputs/`
放配置和本次任务输入，不放采集结果。

#### `raw/`
只放原始采集结果，不写结论性语言。

#### `analysis/`
放中间分析文件，如：
- 候选池筛选结果
- 评分明细
- 评论痛点归类
- 局部总结

#### `outputs/`
只放最终输出：
- `report.md`
- `summary.json`

## 7. 单技能设计方案

首版不做细颗粒度多技能拆分，先做一个主技能即可。

### 7.1 技能命名建议
- **推荐技能名**：`app-store-radar`

### 7.2 技能职责
这个技能首版只负责三件事：

1. **读取配置范围**
   - 主要地区
   - 工具类榜单
   - 扫描频率（手动 / 定时）

2. **执行一次完整扫描与分析**
   - 榜单候选收集
   - App 基础信息提取
   - 评论采样
   - IAP / 价格信息整理
   - 机会判断与建议生成

3. **输出标准 Markdown 报告**
   - Top 3 候选
   - 候选池总览
   - 每个 App 的一句话简介
   - 核心痛点
   - 跟进建议
   - 综合评级

### 7.3 技能内部执行原则
- 技能本身不直接长上下文推理所有原始数据
- 尽量使用文件中间态串联流程
- 多地区 / 多 App 采集时应按批次处理
- 必要时允许调用子智能体分段工作，但输出必须回写到 run 目录

## 8. 评分模型（首版）

首版机会分建议为 `Opportunity Score`，总分 100。

### 8.1 评分维度

#### 热度分（35%）
- 当前榜单位置
- 最近排名变化
- 是否在多个重点地区同时出现

#### 变现分（25%）
- 是否有订阅 / IAP / 买断
- 价格带是否健康
- 收费结构是否清晰

#### 痛点分（30%）
- 中低星差评是否集中在少数问题
- 问题是否高频、明确、可修复

#### 可复制性分（10%）
- 是否偏工具型
- 技术门槛是否适中
- 是否适合做 fast-follower

### 8.2 输出要求
评分不仅给出总分，还应尽量保留可解释性：
- 为什么值得看
- 为什么可能能赚钱
- 为什么存在改进切入点

## 12. 推荐实施顺序

### 阶段 1：跑通数据链路
- 初始化 run 目录
- 生成 `plan.md`
- 跑通榜单采集
- 跑通单 App 基础信息采集

### 阶段 2：跑通评论与价格信息
- 采样评论
- 提取 1~3 星评价

### 阶段 3：跑通分析与模板输出
- 建立候选池
- 生成机会分
- 输出稳定 Markdown 报告
- 输出飞书摘要消息

### 阶段 4：优化质量
- 优化评分规则
- 增强异常处理
- 加入必要的子智能体分段处理
- 控制上下文大小和失败恢复

---

## 13. 成功标准

首版如果达到以下标准，就算可用：

1. 能稳定按一次执行生成独立 run 目录
2. 能先产出 `plan.md` 再执行后续流程
3. 能把原始数据与分析结果分层落文件
4. 能输出稳定格式的 `report.md`
5. 能生成飞书可读的 Top 3 摘要
6. 在多地区扫描时，不因上下文爆炸导致报告结构混乱或结论明显失真

## 14. 后续扩展方向

二期可考虑：
- 接入 Google Play
- 接入飞书多维表格 / Notion
- 增加历史趋势对比
- 增加“跨地区同步冒头”预警
- 增加更细的多技能拆分
- 增加定时调度与失败重试策略

---

## 15. 结论

这个 Agent 首版不追求“功能多”，而追求三件事：
- **流程稳定**
- **上下文可控**
- **输出可复用**

因此，设计重点必须放在：
- 临时目录隔离
- 计划文件先行
- 文件中间态
- 必要时子智能体分段处理
- 稳定 Markdown 模板输出

只要这套骨架先跑顺，后续再扩地区、扩平台、扩结构化输出都会很自然。
